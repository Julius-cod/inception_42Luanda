Infrastructure

O que é o Inception

O Inception é um projeto de sistemas e infraestrutura da 42. O objetivo é construir um ambiente com vários serviços, cada um isolado no seu container, com dados persistentes, comunicação por rede interna, reverse proxy e TLS.

Isolamento e containerização

Cada serviço é construído a partir do seu próprio Dockerfile e corre num container separado. Uma falha ou alteração num serviço não contamina os outros, e cada um contém apenas o que precisa.

O papel do Docker Compose

Um ficheiro YAML descreve os serviços, a configuração de build, redes, volumes, portas, variáveis de ambiente, dependências e secrets. O YAML não executa nada por si: é o Docker Compose que interpreta esta configuração e cria os recursos.

Persistência e descoberta de serviços

Os dados do WordPress e da MariaDB vivem em volumes, independentes do ciclo de vida dos containers. Na rede bridge, cada serviço é encontrado pelo nome (por exemplo mariadb) através do DNS interno do Docker.

Reverse proxy e TLS

O Nginx é o único serviço com porta publicada para tráfego web. Termina a ligação TLS e encaminha cada pedido para o serviço interno adequado, pelo protocolo adequado.

Descrição textual da arquitetura
  1. O browser liga-se ao Nginx por HTTPS na porta 443, a única porta web publicada no host.
  2. Para /, o Nginx envia os pedidos PHP por FastCGI ao PHP-FPM do WordPress em wordpress:9000.
  3. O WordPress liga-se à MariaDB em mariadb:3306 e usa o Redis em redis:6379 como cache de objetos.
  4. Para /adminer, o Nginx envia os pedidos PHP por FastCGI ao Adminer em adminer:9001, que por sua vez se liga à MariaDB.
  5. Para /static/, o Nginx serve ficheiros de /var/www/static/ diretamente.
  6. Para /cadvisor/, o Nginx faz proxy HTTP para http://cadvisor:8080/; o cAdvisor lê métricas do runtime Docker.
  7. O vsftpd aceita ligações FTP de controlo na porta 21 e usa portas passivas configuradas para dados; tem acesso ao volume do WordPress.

    Porta interna vs. porta publicada. Uma porta interna (por exemplo 3306) só é alcançável por outros containers na mesma rede Docker. Uma porta publicada (ports: no Compose) fica acessível a partir do host. Neste projeto, o tráfego web entra apenas pela 443; o FTP exige a porta 21 e o intervalo passivo configurado.

    Docker deep dive

    Conceitos Docker, na prática

    Os conceitos que tornam esta arquitetura possível, explicados com exemplos.

    Image vs. container
    A image é um conjunto de camadas só de leitura com sistema de ficheiros e metadados. O container é uma instância em execução, com uma camada de escrita própria. Várias instâncias podem nascer da mesma image.
    Dockerfile vs. image
    O Dockerfile é a receita (FROM, RUN, COPY, ENTRYPOINT…). docker build executa essa receita e produz a image.
    FROM debian:bookworm
RUN apt-get update && apt-get install -y nginx openssl
COPY conf/nginx.conf /etc/nginx/nginx.conf
ENTRYPOINT ["nginx", "-g", "daemon off;"]
    Exemplo ilustrativo; a versão base e os ficheiros reais dependem do projeto.
    Volume vs. filesystem do container
    Tudo o que é escrito na camada do container perde-se quando ele é removido. Um volume é montado a partir de fora e sobrevive à recriação, por isso guarda a base de dados e os ficheiros do WordPress.
    Rede bridge e descoberta por DNS
    Numa rede bridge definida pelo utilizador, o Docker fornece DNS interno: o WordPress liga-se a mariadb:3306 pelo nome do serviço, sem IPs fixos.
    Variáveis de ambiente vs. Docker secrets
    Variáveis de ambiente são práticas para configuração não sensível, mas ficam visíveis em docker inspect. Secrets são montados como ficheiros (em /run/secrets/) e são preferíveis para palavras-passe. Nenhum segredo deve estar no repositório.
    Porta do container vs. porta publicada
    expose ou a simples escuta numa porta só a torna acessível na rede interna. ports: ["443:443"] publica-a no host. Menos portas publicadas significa menor superfície de ataque.
    Reverse proxy vs. FastCGI
    Num reverse proxy HTTP (proxy_pass), o Nginx reencaminha um pedido HTTP para outro servidor HTTP — é o caso do cAdvisor. Com FastCGI (fastcgi_pass), o Nginx fala um protocolo binário com o PHP-FPM, que executa o script PHP — é o caso do WordPress e do Adminer.
    Certificados TLS
    O Nginx apresenta um certificado e cifra a ligação com o browser (TLSv1.2/1.3). Num ambiente de avaliação o certificado é normalmente autoassinado, pelo que o browser mostra um aviso. TLS protege o transporte; não protege a aplicação por si só.
    Dependências e ordem de arranque
    depends_on define a ordem de arranque dos containers, mas não garante que o serviço esteja pronto. Por isso, o script de entrada do WordPress deve esperar até a MariaDB aceitar ligações.
    docker-compose.yml · excerto sanitizado
    services:
  wordpress:
    build: ./requirements/wordpress
    image: wordpress
    container_name: wordpress
    depends_on:
      - mariadb
    env_file: .env
    secrets:
      - db_password
    volumes:
      - wordpress_data:/var/www/html
    networks:
      - inception
    restart: always
    # sem "ports:": 9000 só é acessível na rede interna

networks:
  inception:
    driver: bridge

secrets:
  db_password:
    file: ../secrets/db_password.txt  # conteúdo nunca publicado
    • build — diretório com o Dockerfile usado para criar a image.
    • image — nome atribuído à image construída.
    • depends_on — ordem de arranque, não verificação de prontidão.
    • env_file — carrega variáveis não sensíveis de um ficheiro.
    • secrets — monta dados sensíveis em /run/secrets/.
    • volumes — liga um volume persistente a um caminho do container.
    • networks — rede onde o serviço é descoberto pelo nome.
    • restart — política de reinício em caso de falha.

    Security

    Segurança e honestidade técnica

    Exposição mínima

    • Apenas a 443 é publicada para tráfego web; MariaDB, Redis e PHP-FPM ficam na rede interna.
    • Adminer e cAdvisor passam pelo Nginx e devem estar protegidos com autenticação.
    • O FTP é o único serviço adicional com portas publicadas, por necessidade do protocolo.

    Limites deste site

    • É uma página estática: não consulta o Docker nem verifica a saúde dos serviços.
    • Indicações como “Configurado” ou “Expected route” descrevem a configuração, não medições.
    • TLS cifra o transporte, mas não corrige vulnerabilidades da aplicação.
    • Nenhuma palavra-passe, segredo ou valor de ambiente é apresentado aqui.

    Glossary

    Glossário técnico

    12 termos
    Container
    Processo isolado criado a partir de uma image, com sistema de ficheiros, rede e recursos próprios.
    Image
    Template só de leitura, construído a partir de um Dockerfile.
    Dockerfile
    Ficheiro de instruções para construir uma image.
    Docker Compose
    Ferramenta que interpreta um ficheiro YAML e cria serviços, redes e volumes.
    Volume
    Armazenamento persistente gerido fora do ciclo de vida do container.
    Bridge network
    Rede virtual privada entre containers, com DNS por nome de serviço.
    Reverse proxy
    Servidor que recebe pedidos dos clientes e os encaminha para serviços internos.
    PHP-FPM
    FastCGI Process Manager: gere os processos que executam código PHP.
    FastCGI
    Protocolo entre um servidor web e um processo de aplicação, como o PHP-FPM.
    TLS
    Protocolo que cifra e autentica a ligação entre cliente e servidor.
    Docker secret
    Dado sensível montado como ficheiro dentro do container.
    PID 1
    Processo principal do container; quando termina, o container para.

    What I learned

    O que aprendi

    Construir cada image a partir do zero obrigou-me a perceber o que cada serviço precisa realmente para funcionar — e o que não precisa.

    Aprendi a distinguir configuração de execução: o YAML descreve, o Compose cria, e cada container deve ter um único processo principal bem comportado como PID 1.

    Percebi que o routing do Nginx é uma decisão de arquitetura: escolher entre servir ficheiros, FastCGI ou proxy HTTP define como os serviços comunicam e o que fica exposto.

    Acima de tudo, aprendi a pensar em superfície de ataque: cada porta publicada e cada painel de administração precisam de uma justificação.
